# Known issues

Honest list of unresolved problems. Empty means none found so far; new items are appended with severity, root cause, attempts and workaround. No P0/P1 functional gaps are acceptable at Gate 6.

| # | Severity (P0–P3) | Area | Symptom | Root cause (known/suspected) | Attempts | Workaround |
|---|---|---|---|---|---|---|
| 1 | P0 | Scripts / CLI | `remove-db.bat`, `dummy-db.bat`, `restore-db.bat` were absent; CLI had no `db-dummy`, `db-restore`, or verified backup machinery. The three scripted workflows required by brief 04 could not run at all. | Tools were never implemented beyond the `setup.bat` / `start.bat` wrappers. | Implemented the three `.bat` wrappers and wired `db-dummy`, `db-restore`, enhanced `db-reset`, `BackupService` and `DummyGenerator` into `src/FixNGo.Cli`. | None needed after the fix. |
| 2 | P1 | `setup.bat`, `start.bat` | Script event logs were always written to the project `logs\` folder and `start.bat` always wrote `data\server.port`, ignoring the isolated `FIXNGO_LOG_DIR` / `FIXNGO_DATA_DIR` used by the automated tests. S1/S10 could pollute the real project `data\` folder. | Hard-coded relative paths in the batch wrappers. | Changed log root and data dir to honour the environment variables, with the original paths as defaults. | None needed after the fix. |
| 3 | P1 | Backup / restore | A backup created with `VACUUM INTO` was internally consistent but not byte-identical to the live DB, so S6/S9 SHA-256 equality assertions failed after restore. | `VACUUM INTO` rewrites the SQLite file layout even when the logical data is identical. | `BackupService` now writes a `consistent-vacuum.db` for verification (hash/integrity/user count) but copies the checkpointed raw DB bytes into the retained backup. | None needed after the fix. |
| 4 | P1 | Dummy generator | First dummy-generation attempt failed with `UNIQUE constraint failed: Users.Email`; a second attempt failed because SQLite briefly kept `consistent-vacuum.db` open. | Email suffix used the per-role index instead of the global account index, causing collisions across roles; file deletion raced SQLite cleanup. | Used the global index for the email suffix and made temporary-vacuum cleanup best-effort. | None needed after the fix. |
| 5 | P3 | `start.bat` | Timestamp format string `yyyyMMdd-Hmmmss` produced ambiguous log filenames. | Typo in the batch wrapper. | Corrected to `yyyyMMdd-HHmmss`. | None needed after the fix. |
| 6 | P3 | Dummy dataset / test contract | `Suspended` dummy users are intentionally not generated. | The API correctly refuses `Suspended` accounts at login, which would break S4's “every listed credential logs in” assertion. The generated set covers `Active`, `PendingVerification` and `DeletionRequested` instead. | Documented here and in `docs/SCRIPT_TESTS.md`; S4 verifies all 201 generated credentials log in. | None needed; this is a deliberate dataset choice, not a product defect. |
| 7 | P3 | Logging / `ExceptionMiddleware` | During the rapid E2E screen sweep a client-cancelled `GET /api/v1/sim/push` was logged `ERROR "Unhandled exception"` and mapped to a 500, despite being a normal client abort. | The generic `catch (Exception)` treated `TaskCanceledException` (an `OperationCanceledException`) as a server fault. | Added explicit `OperationCanceledException` handlers in `src/FixNGo.Web/Middleware/ExceptionMiddleware.cs`: client-aborted requests log at Debug and write no response; other cancellations also log at Debug. The middleware no longer emits a false 500 or an `ERROR "Unhandled exception"` line. EF Core may still emit its own connection-cancellation diagnostic at ERR level when the client disconnects mid-query; that is a provider diagnostic, not an app fault, and no 500 reaches the client. | None needed after the fix; full suite re-run confirms no regression. |
